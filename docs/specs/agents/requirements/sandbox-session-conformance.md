# Sandboxed session requirements

## Overview

Extends [Sandbox policy requirements](sandbox-policies.md), which own every behavior not restated here (guarded surface: REQ-AGENTS-SANDBOX-009 and -010 in that file; [guarded surface design](../system-design/sandbox-guarded-session-surface.md)). [Design](../system-design/sandbox-session-conformance.md) owns mechanisms, tables and reason sets. Related: [macOS support](sandbox-macos-support.md), [session control-plane isolation](../../executors/requirements/session-control-plane-isolation.md).

This file defines when Kandev may call a session sandboxed. Individual mechanisms are owned elsewhere; this file owns the end-to-end contract and the release gate that proves it.

Every guarantee item ends in one of three outcomes: the guarantee holds, the launch is refused with a reason, or the session shows as degraded with a reason. A launch that proceeds while an item is silently unmet is a defect. A refusal never stops the backend from serving other work. The guarantee items are AC-AGENTS-SANDBOX-012.1 to 012.12 and 012.16. Numbers are identifiers, not an order; the order is in Boundaries and defaults.

## Requirements

### REQ-AGENTS-SANDBOX-012: Sandboxed session

**Intent:** An operator who selects a sandbox can rely on the session being confined as promised, or is told exactly why not, on every supported host and agent.

- **AC-AGENTS-SANDBOX-012.1:** When the sandbox feature is enabled and sandbox setup is unavailable on the host, Kandev shall keep serving, shall refuse each launch that requires a sandbox with class `sandbox_runtime_unavailable` and one reason code, and shall return that code with localized text and a remedy in the Settings availability response.
  Reason codes, in precedence order, the first that applies being reported: `state_root_denied` (the data directory traverses a symlink, or on darwin is under a temporary root), `state_root_unusable`, `provider_missing`, `provider_unavailable`. The availability response keeps `blocker` and gains an additive `reason_code`. Unsandboxed launches are unaffected. The backend never exits because of this condition, whatever any flag says. `state_root_*` is fixed at startup; provider conditions are read uncached on every availability read and admission, so installing the provider clears `provider_missing` without a restart.
- **AC-AGENTS-SANDBOX-012.2:** When a sandboxed agent exits, or times out, before its protocol handshake completes, the session error shall carry a bounded cause and shall name it in Execution details and the session error card.
  Causes, in precedence order: `agent_binary_denied`, `agent_credentials_missing`, `sandbox_denied_other`, `agent_handshake_timeout`, `agent_exited`. Agentctl derives the cause and sends core only that; stderr text is never sent, stored, or shown. With none derivable the cause is `agent_exited`. The cause is decided once per attempt, an exit winning over a simultaneous timeout. It is persisted as `launch_cause`; if persisting fails the live error still shows it and item 012.2 is `unknown`.
- **AC-AGENTS-SANDBOX-012.3:** A session shall have its policy pinned at launch, and a later policy, binding, or executor change shall not alter a running attempt.
  A continuation (a prompt turn or ACP reload on a live attempt) runs no admission. A resume, recovery or replacement that starts a new agent process or instance re-runs the admission checks of Boundaries and defaults against current host state, keeps the pinned revision (AC-AGENTS-SANDBOX-002.5) and creates a new attempt with a new summary; the token follows the instance; an adopted retained instance continues its attempt and summary. A refused re-admission writes a refusal record, keeps the conversation and leaves the session resumable; the operator-started retry is a new launch that resolves the current binding.
- **AC-AGENTS-SANDBOX-012.4:** In a guarded session (one whose pinned attempt carries a task guard, REQ-AGENTS-SANDBOX-009), the Kandev MCP tool surface shall be enforced by the server for every tool class, and no mutating tool shall be auto-approved. This criterion is satisfied by REQ-AGENTS-SANDBOX-009 and -010 and is exercised by the canary `G1_mcp_unguarded_tool` (012.13).
  A mutating tool is one classed anything other than `read` or `self`; classes `read` and `self` may be auto-approved by AC-AGENTS-SANDBOX-010.2 and `self` tools act only on the caller's own task.
- **AC-AGENTS-SANDBOX-012.5:** Agent-facing MCP routes shall accept only the session token of the calling agentctl instance, and the Git credential broker shall be reachable by the agent only through that instance's own relay. A request with no token or another instance's token shall be rejected with 401, and a request to an instance whose token was revoked with 503 `mcp_token_unconfigured` (or a refused connection once the instance is deleted), each with no side effect.
  This criterion is satisfied by REQ-EXECUTORS-SESSION-CONTROL-ISOLATION-001 and -002, which own the mechanism: the token is bound to one instance and stays the same across agent restart within it (001.9), a new instance has a new token, the relay needs no token because its authorization is the lease in the body (002.11), and no broker setting given to the agent contains the backend host (002.10). When an attempt ends the instance is deleted or its token revoked, except that an instance retained for a successor attempt of the same session keeps its token until its last attempt ends. A request already past validation may finish and long-lived MCP streams of the instance are closed. A teardown failing both revoke and delete is retried until one succeeds.
- **AC-AGENTS-SANDBOX-012.6:** Every route of the agentctl instance router shall require the instance credential, except routes on a fixed exemption list that carry their own credential or expose no state, and a request without or with a wrong, malformed, or stale credential shall be rejected with status 401 and an identical body before any handler runs. A sandboxed attempt shall run only on an instance that reports `rest_auth` as `enforced`.
  The exemption list is `/health` (no state), `/sse`, `/message`, `/mcp` (each gated by the session token of 012.5) and `/git-credentials/` (gated by the lease, 012.5). A path is exempt only when its cleaned form equals its raw form and an exempt path (or lies below `/git-credentials/`); `/MCP`, `/mcpx` and `/sse.` are not. The control router keeps its own rules (AC-EXECUTORS-CONTROL-OWNERSHIP-002.7 and -002.9) and a second enumeration test holds it to them. An instance with no credential configured reports `rest_auth` `none` and passes unsandboxed attempts through; a sandboxed launch on it is refused with `sandbox_rest_auth_unenforced`. A test enumerates every instance-router route and fails when one is neither authenticated nor listed.
- **AC-AGENTS-SANDBOX-012.7:** Managed Git operations performed by Kandev on a sandboxed task's repository shall run no code supplied by that repository, unless the repository explicitly opts in. This criterion is satisfied by REQ-AGENTS-GITISOLATION-001 to -003 and is exercised by the `G3_repo_*` canaries (012.13), which drive Kandev-run Git.
- **AC-AGENTS-SANDBOX-012.8:** Every process that Kandev starts on behalf of a sandboxed attempt shall run inside the attempt's pinned sandbox or be recorded as `unsandboxed` with its kind before the process starts.
  Kinds are a closed set: `setup_script`, `cleanup_script`, `custom_script`, `dev_process`, `language_server`, `agent_terminal`, `user_terminal`, `code_server`, `helper` (Kandev-internal processes that run no repository or agent code, including managed Git). In this version only `agent_terminal` runs inside the sandbox and every other kind is `unsandboxed`. The agent and its own processes are inside the sandbox by construction. If the label cannot be recorded the process is not started and the start fails with `process_label_unrecorded`. A process whose sandbox state cannot be determined is recorded `unsandboxed`. An `agent_terminal` on a host where `sandbox_transport_unsupported` applies is refused; the refusal does not remove `user_terminal`.
- **AC-AGENTS-SANDBOX-012.9:** Preview content of a sandboxed attempt (HTML preview and session port proxy) is served from the Kandev UI origin in this version, so the first preview served for an attempt shall mark item 012.9 `degraded` with reason `preview_same_origin` for the rest of that attempt.
  Before any preview is served the item `holds`. A served preview is an HTML preview publish or a port-proxy request for a session of the attempt; core fires `preview_state_changed` on the first and commits the state before any preview byte is sent; concurrent first requests serialize on it. If the commit fails the request is refused with 503 `preview_state_unrecorded` and nothing is served. A request with no live attempt is served and counts for none; with the summary flag off nothing is recorded. The state is sticky, and a replacement attempt starts at `holds`. The separate origin is Out of scope.
- **AC-AGENTS-SANDBOX-012.10:** The child environment shall contain only variables named by the policy's environment allowlist, the fixed minimal set core defines, and the Kandev-injected set the design lists, and a variable that is not allowed shall be absent, not empty.
  Matching is exact on name. An allowlisted name that collides with an injected name is ignored and reported `shadowed`; one that collides with a minimal name has no effect. A name on the allowlist whose value in the launch environment is missing or empty is absent from the child and reported `missing`, on every host. Reports list names only, sorted ascending, never values.
- **AC-AGENTS-SANDBOX-012.11:** Each supported agent shall declare its credential methods in a registry keyed by agent and host platform, and a sandboxed launch shall be refused when no declared method can be satisfied on the host.
  Methods are a closed set of kinds: `env_key`, `file_in_agent_state`, `host_keychain`, `none`. An `env_key` method is satisfied when the policy allowlists the name and the launch's resolved environment (before the policy filter) has a non-empty value. A `file_in_agent_state` method is satisfied when the policy grants `agent_state` and the named relative file already exists in the session's agent state, is non-empty and readable; an I/O error is not satisfied. A first launch has an empty agent state, so only `env_key` can satisfy it (provisioning is Out of scope). `host_keychain` is never satisfied under a sandbox. `none` is always satisfied. The launch is satisfied when any one method is. Refusals: `sandbox_credentials_unsupported` when every method is `host_keychain`; `sandbox_credentials_missing` when a satisfiable method exists but none is satisfied; `sandbox_credentials_unknown` when the agent is absent from the registry or its entry has no method. Each names the agent, platform and method kinds. Admission checks presence only; validity appears as `agent_credentials_missing` (012.2). Credential values never cross into the registry, a report, or an error.
- **AC-AGENTS-SANDBOX-012.12:** Kandev shall treat only Local and Worktree executors as able to host a sandboxed session, shall report every other executor type as unsupported in the Settings availability response, and shall refuse sandboxed launches on it with `sandbox_host_unsupported` and reason `executor_unsupported`.
  A Local or Worktree executor on a host that cannot confine keeps AC-AGENTS-SANDBOX-011.2 and its refusal carries reason `host_cannot_confine`. There is no third state and no probe in this version (Out of scope). The Settings response lists every executor type with `supported` and a reason code; the launch check uses the same table.
- **AC-AGENTS-SANDBOX-012.13:** The release gate shall be a conformance suite that runs the operator journey with a real agent on a real host and, for every canary listed in the design, a probe paired with a control proving the probe can detect the escape. A probe result is valid only if its control detected the escape.
  Canary states are `contained`, `escaped`, `invalid` (control did not detect), `not_applicable` (closed reason list in the design) and `error` (infrastructure failure, timeout, crash or a target absent on a host that should have it). Only `contained` passes; `escaped`, `invalid` and `error` fail the run; `not_applicable` neither passes nor fails; a failure to run is never counted as `contained`. The suite prints probe identifiers and outcomes only, never a file name outside its fixture root, a credential, or a token.
- **AC-AGENTS-SANDBOX-012.14:** Execution details shall show for the current attempt the state of every guarantee item with its reason code, and a session shall be shown as confined only when every item is `holds` or `not_applicable`.
  Item states: `holds`, `degraded`, `not_applicable`, `unknown`, `refused` (this item caused the refusal). The summary is `refused` when the launch was refused, else `degraded` when any item is `degraded` or `unknown`, else `confined`. State is derived from the pinned attempt and the design's events, never from current settings. The current attempt is the live attempt when the session has one, else the newer of the latest attempt and the latest refusal record of the session, by creation time then id; a refusal recorded while an attempt is live is listed in Execution details as the latest refused launch and does not replace it. The indicator follows the design matrix of the 008.2 status and the summary: failed for `refused` or status `failed`, a warning for `degraded`, the shield only for `confined` with an active status, each opening Execution details with localized reason and remedy; unknown or missing items are ignored.
- **AC-AGENTS-SANDBOX-012.16:** A sandboxed attempt on Local or Worktree shall run only on an agentctl instance whose actual listener is loopback, otherwise the launch is refused with `sandbox_bind_exposed` and reason `bind_exposed`.
  Loopback means the listener address is in 127.0.0.0/8 or is ::1. Agentctl reports `bind` (`loopback`, or `exposed` when its instance listener or its control listener is not loopback, computed from the real listeners) in the instance `/identity`; an instance that reports nothing, or whose `/identity` cannot be read in one 5 s attempt, is refused with reason `bind_unreported`. The managed launcher listens on `agent.standaloneHost` (default loopback); a non-loopback value is honored and, with `features.agentctlLoopbackBind` on, refused as reported. A non-loopback dial host is refused with the same code whatever the flag state. The code-server of a sandboxed attempt binds loopback too. Other executors keep their bind.

## Boundaries and defaults

- **Evaluation order.** At launch the checks run in this fixed order and the first unmet one refuses the launch: 012.1 (in `sandboxLaunchAdmission.admit`, after policy resolution), then in `prepareExecution`: 012.12 including 011.2, then 012.16, then the `rest_auth` check of 012.6, then 012.11. Items after the refusing one are recorded `unknown` with reason `not_evaluated`. The instance `/identity` is read once per launch (5 s); if that read fails (timeout, non-200 or malformed body) the first check that needs it, the host test of 011.2, refuses with reason `identity_unreadable`, and a readable body that omits a field gives that field's `*_unreported` code. 012.3 applies on resume; 012.2, 012.5, 012.8, 012.9 and 012.10 are runtime items.
- **Refusal record.** With `features.sandboxSessionSummary` on, a refused launch writes a launch refusal record, a table separate from attempts holding the refusal code, reason and evaluated items; it creates no attempt, runs no provider compile, process or runtime root, and is invisible to every attempt reader. A refusal before any item runs (no policy resolves) records every item `unknown` `not_evaluated`. The latest 20 records per session are kept; older ones are pruned on write. If the write fails the launch is still refused and the failure is logged.
- **Idempotency.** Each launch request writes its own refusal record; a refusal never mutates policy or bindings; retry re-runs admission. A sandbox refusal is never retried automatically; only an operator-started launch retries.
- **Concurrency.** Two launches on one executor are admitted independently. A token is allocated per instance.
- **Flags.** `features.sandboxSessionSummary` (off) gates the summary, refusal records, the refusals and codes of 012.11, 012.12, 012.16 and the `rest_auth` check, process labels and exit causes. These stay ungated hardening: the 012.1 keep-serving and `reason_code`, 012.5, and the 012.6 route rule and identical 401. `features.agentctlLoopbackBind` is consulted only while the summary flag is on and takes effect at admission without a restart: with it off 012.16 is `degraded` `feature_disabled` for an exposed listener and the code-server bind is unchanged. With the summary flag off behavior is that of REQ-AGENTS-SANDBOX-008 and -011 plus the ungated items. An attempt live when the flag is turned off gets no further events; the first dropped event sets the `evidence_gap` latch (evidence design) for every runtime item, so those items stay `unknown` `evidence_unavailable` even if the flag returns. Attempts admitted while the flag was off never get a summary; refusal records are hidden, not deleted, while it is off.
- **Amendments when the summary flag is on.** AC-AGENTS-SANDBOX-011.2 gains the reason codes of 012.12; 011.3's last two sentences are replaced by 012.11 (a keychain-only agent is refused); 011.4's denied state root gains `reason_code`; the 011 Exclusions item "persisted launch-cause carrier" is delivered for the 012.2 causes; AC-AGENTS-SANDBOX-008.3's indicator follows 012.14.
- **Defaults.** `features.sandboxPolicies` is off in every shipped profile. Non-Local, non-Worktree executors are unsupported. An agent absent from the registry is refused. A session that predates this requirement has no summary.

## Out of scope

- **Separate preview origin (cut).** A per-task origin with a single-use ticket and host-only cookie for HTML preview and the session port proxy, behind ADR `2026-10-26-sandboxed-preview-origin`. A follow-up needs wildcard DNS and TLS, the ticket lifecycle, a transaction rule between origin creation and launch, a barrier for tasks that gain a guard, and browser proof that a preview page cannot read UI cookies. Until then 012.9 is a degraded label.
- **Agent credential provisioning (cut).** Copying a Kandev-owned seed directory into a new session's agent state so a file login satisfies `file_in_agent_state` on the first launch. A follow-up needs atomic publication under concurrent first creation, a partial-copy rule and measured file names per agent. Until then a first launch relies on `env_key`.
- **Child ceiling (cut).** A creation-time check that a child of a guarded parent resolves no broader policy than its guards (`sandbox_outside_ceiling`, no row). A follow-up must decide the ceiling for incomparable or absent parent and caller guards (propose: no broader than each guarded source), which existing `ErrIneligible` results become the new code, and the REST status, MCP error and text.
- **Child grant narrowing (cut).** A `sandbox_grants` request on REST and MCP create-task that narrows a child below its parent guard, with a stored `narrowing` and an effective policy compiled at launch. A follow-up needs the omitted-versus-explicit rule per dimension and the lock on the calling task's guard.

- Windows hosts, a host probe for remote executor types (follow-up: per-type probe proving confinement before first launch), sandboxing of setup, cleanup and custom scripts, dev processes, language servers, code-server and user terminals (labelled `unsandboxed` in this version), and agents beyond `claude-acp`, `codex-acp` and the e2e mock agent.
- Git commit and push on macOS in the conformance journey (excluded by AC-AGENTS-SANDBOX-011 Exclusions: identity and common-git-directory writes).
- Network egress beyond the policy's exact destinations; owned by REQ-AGENTS-SANDBOX-005.
- Approvals on macOS (REQ-AGENTS-SANDBOX-011 excludes them).
- A short-lived-token broker for keychain-based agent login under a macOS sandbox.
