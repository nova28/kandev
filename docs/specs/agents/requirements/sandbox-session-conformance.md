# Sandboxed session requirements

## Overview

Extends [Sandbox policy requirements](sandbox-policies.md), which own every behavior not restated here (guarded surface: REQ-AGENTS-SANDBOX-009 and -010 in that file; [guarded surface design](../system-design/sandbox-guarded-session-surface.md)). Its terms apply. [Design](../system-design/sandbox-session-conformance.md). Related: [macOS support](sandbox-macos-support.md).

This file defines when Kandev may call a session sandboxed. Individual mechanisms are owned elsewhere; this file owns the end-to-end contract and the release gate that proves it.

Every guarantee item ends in one of three outcomes: the guarantee holds, the launch is refused with a reason, or the session shows as degraded with a reason. A fourth outcome, a launch that proceeds while an item is silently unmet, is a defect in every case. A refusal never stops the backend from serving other work. The guarantee items are AC-AGENTS-SANDBOX-012.1 to 012.12, 012.15 and 012.16. Their numbers are identifiers, not an evaluation order; the order is in Boundaries and defaults.

## Requirements

### REQ-AGENTS-SANDBOX-012: Sandboxed session

**Intent:** An operator who selects a sandbox can rely on the session being confined as promised, or is told exactly why not, on every supported host and agent.

- **AC-AGENTS-SANDBOX-012.1:** When the sandbox feature is enabled and sandbox setup is unavailable on the host, Kandev shall keep serving, shall refuse each launch that requires a sandbox with class `sandbox_runtime_unavailable` and one reason code, and shall return that reason code in the Settings availability response.
  Reason codes are a closed set: `state_root_denied` (the data directory is under a temporary root or traverses a symlink), `state_root_unusable`, `provider_missing`, `provider_unavailable`. A host that cannot confine keeps the shipped class `sandbox_host_unsupported` (012.12). The availability response keeps its `blocker` field unchanged and gains an additive `reason_code`. Unsandboxed launches are unaffected. The backend never exits because of this condition, whatever the state of any feature flag. `state_root_*` conditions are fixed at startup; provider conditions are re-evaluated on every availability read and every admission, so installing the provider clears `provider_missing` without a restart.
- **AC-AGENTS-SANDBOX-012.2:** When a sandboxed agent exits, or times out, before its protocol handshake completes, the session error shall carry a bounded cause and shall name it in Execution details and the session error card.
  Causes are a closed set: `agent_binary_denied`, `agent_credentials_missing`, `sandbox_denied_other`, `agent_handshake_timeout`, `agent_exited`. Agentctl derives the cause and sends core only the cause; stderr text is never sent to core, stored, or sent to the client. If no cause can be derived, including empty stderr and death by signal, the cause is `agent_exited`. Precedence when several match is the order listed. The cause is persisted on the attempt record as `launch_cause`.
- **AC-AGENTS-SANDBOX-012.3:** A session shall have its policy pinned at launch, and a later policy, binding, or executor change shall not alter a running attempt.
  Continuation, recovery, and replacement keep the pinned revision (AC-AGENTS-SANDBOX-002.5) and re-run the admission checks of Boundaries and defaults against current host state. A retry of a refused launch is a new launch that resolves the current binding.
- **AC-AGENTS-SANDBOX-012.4:** In a guarded session, the Kandev MCP tool surface shall be enforced by the server for every tool class, and no mutating tool shall be auto-approved. This criterion is satisfied by REQ-AGENTS-SANDBOX-009 and -010 and is exercised by the canary `G1_mcp_unguarded_tool` (012.13).
  Here a mutating tool is one classed anything other than `read` or `self`; classes `read` and `self` may be auto-approved by AC-AGENTS-SANDBOX-010.2 and `self` tools act only on the caller's own task.
- **AC-AGENTS-SANDBOX-012.5:** Agent-facing MCP routes and the Git credential broker shall accept only the per-session token of the calling instance, and a request carrying another session's token, no token, or the token of a finished attempt shall be rejected with status 401 and no side effect.
  The token is bound to one agentctl instance and one attempt generation, is not logged, and is revoked when the attempt ends. A replacement attempt receives a new token. After revocation completes no new side effect starts; a request already past validation may finish; long-lived MCP streams of that attempt are closed. The mechanism is owned by the standalone MCP session token requirement; this criterion fixes the observable contract.
- **AC-AGENTS-SANDBOX-012.6:** Every agentctl REST route shall require the instance credential, except routes on a fixed exemption list that each carry their own credential or expose no state, and a request without or with a wrong, malformed, or stale credential shall be rejected with status 401 and an identical body before any handler runs.
  The exemption list is `/health` (no state), `/sse`, `/message`, `/mcp` and the Git credential relay prefix (each gated by the session token of 012.5). A test enumerates every registered route and fails when a route is neither authenticated nor on the list.
- **AC-AGENTS-SANDBOX-012.7:** Managed Git operations performed by Kandev on a sandboxed task's repository shall run no code supplied by that repository, unless the repository explicitly opts in. This criterion is satisfied by REQ-AGENTS-GITISOLATION-001 to -003 and is exercised by the canaries `G3_repo_*` (012.13), which drive Kandev-run Git, not agent-issued Git.
- **AC-AGENTS-SANDBOX-012.8:** Every process that Kandev starts on behalf of a sandboxed attempt shall either run inside the attempt's pinned sandbox or be recorded as `unsandboxed` with its kind before the process starts.
  Kinds are a closed set: `setup_script`, `cleanup_script`, `custom_script`, `dev_process`, `language_server`, `terminal`, `code_server`, `helper`. The agent itself and the processes it starts are inside the sandbox by construction and are not Kandev-started. If the label cannot be recorded the process is not started and the start fails with `process_label_unrecorded`. A process whose sandbox state cannot be determined is recorded `unsandboxed`. A native terminal on a host where `sandbox_transport_unsupported` applies is refused; no unsandboxed terminal is offered for a sandboxed task.
- **AC-AGENTS-SANDBOX-012.9:** Preview content produced by a sandboxed attempt (HTML preview and session port proxy) shall be served from an origin different from the Kandev UI origin, and a preview page shall not be able to read Kandev UI cookies or storage.
  When no separate origin can be provided, or its flag is off, the preview is disabled with reason `preview_origin_unavailable` instead of being served from the UI origin. The origin is derived per task, is stable for the task's life, and is never reused across tasks or after the task is deleted.
- **AC-AGENTS-SANDBOX-012.10:** The child environment shall contain only variables named by the policy's environment allowlist plus the fixed minimal set the provider documents, and a variable that is not allowed shall be absent, not empty.
  Matching is exact on name. A name on the allowlist whose host value is missing or empty is absent from the child and reported as `missing`. Values are never written to logs or reports; reports list names only.
- **AC-AGENTS-SANDBOX-012.11:** Each supported agent shall declare its credential methods in a registry keyed by agent and host platform, and a sandboxed launch shall be refused when no declared method can be satisfied on the host.
  Methods are a closed set of kinds: `env_key`, `file_in_agent_state`, `host_keychain`. An `env_key` method is satisfied when the policy allowlists the name and the launch environment has a non-empty value for it at admission. A `file_in_agent_state` method is satisfied when the policy grants `agent_state` and the named relative file exists, is non-empty and is readable in it. `host_keychain` is never satisfied under a sandbox (AC-AGENTS-SANDBOX-011.3 keeps the keychain ungranted). The launch is satisfied when any one method is satisfied. Refusals: `sandbox_credentials_unsupported` when every method is `host_keychain`; `sandbox_credentials_missing` when a satisfiable method exists but none is satisfied; `sandbox_credentials_unknown` when the agent is absent from the registry. Each names the agent, platform and method kinds. Admission checks presence only; validity is runtime and appears as `agent_credentials_missing` (012.2). Credential values never cross into the registry, a report, or an error.
- **AC-AGENTS-SANDBOX-012.12:** Kandev shall treat only Local and Worktree executors as able to host a sandboxed session, and shall report every other executor type as unsupported in Settings and refuse sandboxed launches on it with `sandbox_host_unsupported` and reason `executor_unsupported`.
  There is no third state and no probe in this version. A Local or Worktree executor on a host that cannot confine keeps AC-AGENTS-SANDBOX-011.2. A host probe for remote executor types is a follow-up (Out of scope).
- **AC-AGENTS-SANDBOX-012.13:** The release gate shall be a conformance suite that runs the operator journey with a real agent on a real host and, for every canary listed in the design, a probe paired with a control proving the probe can detect the escape. A probe result is valid only if its control detected the escape.
  Result states for a canary are `contained`, `escaped`, `invalid` (control did not detect), `not_applicable` (closed reason list in the design) and `error` (infrastructure failure, timeout or crash). `escaped`, `invalid` and `error` fail the run; a failure to run is never counted as `contained`. The suite prints probe identifiers and outcomes only; it never prints a real file name outside its fixture root, a credential, or a token. The mapping from each guarantee item to its canaries is a table in the design.
- **AC-AGENTS-SANDBOX-012.14:** Execution details shall show for the current attempt the state of every guarantee item with its reason code, and a session shall be shown as confined only when every applicable item holds or is withheld.
  Item states: `holds`, `degraded`, `unsupported` (the capability is withheld and nothing is exposed), `not_applicable`, `unknown` (the host cannot assess). The summary is `confined` when every applicable item is `holds` or `unsupported`; `degraded` when any is `degraded` or `unknown`; `refused` when the launch was refused. State is derived from the pinned attempt and the attempt events listed in the design, never from current settings. On the desktop session tab and the phone status control the shield shows only for `confined`; `degraded` shows a warning indicator and `refused` a failed indicator, each opening Execution details with localized reason and remedy text.
- **AC-AGENTS-SANDBOX-012.15:** A child task of a guarded parent shall receive grants that are a subset of its parent's guard, and a child creation that requests a wider grant shall be refused with `sandbox_outside_ceiling` and no child row.
  The comparison is on the parent guard's grants by role and access: each requested grant must be contained in a parent grant of the same role with equal or narrower access. A child requesting nothing inherits the parent guard exactly. An unguarded parent imposes no ceiling. The parent guard is read in the same transaction that inserts the child, so concurrent creations are each evaluated against a guard state that existed at their own commit.
- **AC-AGENTS-SANDBOX-012.16:** A sandboxed attempt on Local or Worktree shall run only on an agentctl instance whose actual listener is loopback, otherwise the launch is refused with `sandbox_bind_exposed`.
  Loopback means the listener address is in 127.0.0.0/8 or is ::1. Agentctl reports `bind` (`loopback` or `exposed`, computed from its real listener) in `/identity`; an instance that reports nothing is refused with reason `bind_unreported`. When the flag `features.agentctlLoopbackBind` is on, the launcher starts sandboxed Local and Worktree instances on loopback unless an explicit `agent.standaloneHost` is configured, which wins and is checked as reported. The code-server process of a sandboxed attempt binds loopback too. Other executors keep their present bind.

## Boundaries and defaults

- **Evaluation order.** At launch the checks run in this fixed order and the first unmet one refuses the launch: 012.1 runtime availability and 012.11 credentials (in `sandboxLaunchAdmission.admit`), then 012.12 executor capability including AC-AGENTS-SANDBOX-011.2, then 012.16 bind (in `prepareExecution`, where the instance is known). Items after the refusing one are recorded `unknown` on the refused record, not unmet. A tie within one item is broken by reason code ascending. 012.3 applies on continuation, 012.15 at child creation; 012.2, 012.5, 012.8, 012.9 and 012.10 are runtime items updated by attempt events.
- **Refusal record.** With `features.sandboxSessionSummary` on, a refused launch writes a sandbox attempt in state `refused` holding the evaluated items, with no provider compile, no process and no runtime root. This amends AC-AGENTS-SANDBOX-011.2's "no attempt". If that write fails the launch is still refused and the failure is logged.
- **Idempotency.** Each launch request writes its own refused record; a refusal never mutates policy or bindings; retry re-runs admission.
- **Concurrency.** Two launches on one executor are admitted independently. A token is allocated per attempt and an origin per task.
- **Flags.** `features.sandboxSessionSummary` (off) gates the summary, the refused record, the new reason codes and refusals of 012.11, 012.12 and 012.16, the process labels and the exit causes; the 012.1 keep-serving behavior is not gated. `features.agentctlLoopbackBind` and `features.previewSeparateOrigin` are consulted only while the summary flag is on: with the bind flag off, 012.16 is `degraded` reason `feature_disabled` and not enforced; with the preview flag off, sandboxed previews are disabled (`unsupported`, `preview_origin_unavailable`). With the summary flag off, behavior is exactly that of REQ-AGENTS-SANDBOX-008 and -011.
- **Amendments when the summary flag is on.** AC-AGENTS-SANDBOX-011.3's last two sentences are replaced by 012.11 (a keychain-only agent is refused) and credentials may also arrive as a `file_in_agent_state` file; 011.4's denied state root gains the additive reason code; the 011 Exclusions item "persisted launch-cause carrier" is delivered for the 012.2 causes only; AC-AGENTS-SANDBOX-008.3's shield follows 012.14.
- **Defaults.** `features.sandboxPolicies` is off in every shipped profile. Non-Local, non-Worktree executors are unsupported. An agent absent from the registry is refused. A session that predates this requirement has no summary and shows the existing status only.

## Out of scope

- Windows hosts, a host probe for remote executor types (follow-up: per-type probe proving confinement before first launch), and sandboxing of setup and cleanup scripts (labelled `unsandboxed` in this version).
- An operator-started unsandboxed terminal for a sandboxed task.
- Git commit and push on macOS in the conformance journey (excluded by AC-AGENTS-SANDBOX-011 Exclusions: identity and common-git-directory writes).
- Network egress beyond the policy's exact destinations; owned by REQ-AGENTS-SANDBOX-005.
- Approvals on macOS (REQ-AGENTS-SANDBOX-011 excludes them).
- A short-lived-token broker for keychain-based agent login under a macOS sandbox.
